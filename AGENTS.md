## ОБЯЗАТЕЛЬНЫЙ PREFLIGHT
Если пользователель не задаёт вопрос, а просит изменить код, и правка не очень маленькая, то перед любой задачей агент обязан:
- прочитать этот AGENTS.md;
- кратко подтвердить, что файл прочитан;
- только после этого начинать другие любые действия;

## Проверка типов перед сдачей
После правок в `.vue` / `.ts` агент обязан:
- прогнать `vue-tsc` (или эквивалент) и отфильтровать вывод по затронутым файлам;
- не считать ReadLints достаточным: он часто пустой при ошибках Volar/TS в Vue SFC;
- не писать «готово», пока по затронутым файлам нет TS-ошибок;
- если инструменты чистые, а пользователь видит ошибку — сначала запросить точный текст диагностики, не спорить с IDE.

## Запрет на самостоятельные исправления вне запроса
- Делай только те изменения, которые прямо нужны для задачи пользователя.
- Не добавляй новые абстракции, helper’ы, type alias, константы или промежуточные переменные без необходимости.
- Не выноси простые значения в отдельные переменные, если они используются один раз.
- Если ты видишь улучшение, сначала предложи его пользователю, а не внедряй сразу.
- Предпочитай inline-код для простых одноразовых значений.
- Выносить код можно только при реальном дублировании, сложной логике, улучшении читаемости или явном запросе пользователя.
- Если пользователь сообщает об ошибке после твоих изменений, исправляй только причину этой ошибки.
- Не возвращай старую реализацию, старые стили, старую разметку или прежние HTML-теги, если пользователь явно не попросил откатить именно это.
- Не меняй семантику HTML-тегов (`button`, `article`, `div`, `a` и т.п.) по собственной инициативе.
- Не делай “правильнее”, “семантичнее”, “чище” или “надёжнее”, если это не является прямой причиной текущей ошибки.
- Если видишь соседнюю проблему, сначала напиши пользователю коротко: “Вижу ещё X, поправить?”, и не меняй её без согласия.
- При исправлении ошибки делай минимальный diff: одна причина, одно исправление.
- Сначала найди точную причину ошибки.
- Не меняй другие файлы и участки кода, пока причина не подтверждена.
- Не исправляй попутно стили, HTML-семантику, архитектуру, названия, типы или структуру компонентов.
- Если ошибка связана с одним файлом, правь только этот файл.
- В ответе явно напиши, какую одну причину исправил.

## Non-obvious Nuxt Conventions
- Автоимпорт компонентов и composables отключён через `components: false` и `imports.autoImport: false`. Добавляй явные импорты.
- Nuxt-каталоги перенесены: layouts, middleware и plugins ищутся в `config/layouts`, `config/middleware` и `config/plugins` внутри соответствующего `app`.
- Страницы и сегменты маршрутов с именем, начинающимся на `_`, доступны в dev-режиме, но исключаются из production-сборки через `pages.pattern`.
- SCSS-файлы из `app/config/styles/shared` и `app/common/mixins` автоматически подключаются к каждому SCSS style-блоку. Не добавляй повторные `@use` для них.
- Для навигации импортируй `navigateTo`, `useRoute` и `useRouter` из `~/common/utils/router`. Прямые импорты этих функций из `#app` и `#imports` запрещены ESLint.

- В импортах не разноси один импорт на разные строки. импорт всегда должен быть в одной строке

## CSS-правила
- Все стили компонентов пиши внутри <style scoped> на scss;
- Используй BEM;
- Не обращайся к компонентам через &__element? пиши всегда полные имена классов .block__element;
- Модификаторы вариантов, состояний делай через .block--variant, .block__element--variant;
- Пседоклассы и всевдоэлементы через &:hover, не пиши как в простом css .class:hover;
- Не обращайся к элементам через селекторы, если можно использовать классы. Это не касается файлов глобальных стилей;
- Медиазапросы не пиши в корне css, вставляй их только внутри классов;
- Если нужно задать z-index для компонентов верхнего уровня (`header`, `footer`, `main` и др), а также для fixed - используй переменные из app/config/styles/shared/z-index.scss или создай там новую.

## VUE-правила
- В компонентах делай секцию <script setup lang="ts> всегда сверху, потом template, потом style;
- Смотри библиотеку vueuse https://vueuse.org/ Если можешь использовать её функции, то используй, если это сокращает код.
- Статичные классы указывай в class, динамические в :class. Не смешивай их в одном.
- Не прописывай эмит клика с родительского элемента компонента, его и так можно передать через @click
- Не используй деструктуризацию пропсов, делай withDefaults если нужно
- Внутри шаблона не обращайся к пропсам через props. а обращайся напрямую
- При изменении публичного API компонента соблюдай существующие в проекте паттерны типизации и документирования.
